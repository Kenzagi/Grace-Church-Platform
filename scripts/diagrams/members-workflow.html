Members Section — End-to-End Workflow
From an admin's click to the database and back — the same guard chain protects every write
Phase 1 · Admin UI — Members sectionsrc/components/sections/MembersSection.tsx
1 Browse the directory — table loads via GET /api/members; debounced search (300 ms) plus status, group and household filters re-query the API.
2 Add member — dialog form with client-side Zod rules (gender + maritalStatus required, amber DOB warning); household and groups can be created inline on the fly.
3 Edit member — detail dialog pulls the full profile (household, groups, tags, attendance, submissions) then patches only the changed fields.
4 Upload photo — multipart POST /api/members/[id]/photo; the image is cropped square in the browser flow and stored with the member.
5 Import / export CSV — a three-step wizard (upload → preview → commit) for bulk adds; one click exports the filtered list as CSV.
6 Delete member — confirm dialog, then DELETE /api/members/[id]; memberships, tags and attendance cascade.
↓every action funnels through the same server-side chain
Phase 2 · API guard pipelinerun in order, stop at first failure
7 Rate limit — 60 write requests per minute per IP (login and portal have tighter buckets); excess gets 429 with a Retry-After header.
8 Session + RBAC — the HMAC cookie is verified again inside the handler and the role is checked: only admin and editor may write.
9 Zod validation — createMemberSchema / updateMemberSchema parse the payload; bad input returns 400 with per-field messages.
10 Org scoping + uniqueness — duplicate email inside the org is rejected; every household / group id is proven to belong to the admin's church before it is referenced.
↓all checks passed
Phase 3 · Data layer & response
11 Prisma transaction — the member row and its group memberships are written atomically to SQLite, always stamped with orgId.
12 Audit trail — member.create / member.update / member.delete is recorded with the admin, action, entity and IP.
13 Response — 201 / 200 JSON returns to the UI, the list refetches and a toast confirms; CSV exports stream a file attachment instead.
Error paths — what the admin sees when a step fails
400 — validation failed, duplicate email, or a foreign key from another church
401 — no cookie or expired session → back to the sign-in screen
403 — viewer role attempted a write
404 — member exists but outside your organization (never leaked)
429 — too many requests; UI shows the retry countdown
500 — friendly message; full detail only in the server log
